# Internationalization and Localization (i18n)

## First-release languages

The first release must support:
- English (`en`)
- Polish (`pl`)

The architecture must allow adding more languages later without rewriting UI components.

## Implementation rules

1. Inspect the existing scaffold and its dependencies before choosing an i18n library.
2. Keep translations in separate locale files, preferably `src/locales/en.json` and `src/locales/pl.json` if that fits the project.
3. Every user-visible string must be translated: titles, descriptions, navigation, buttons, form labels, hints, empty states, validation messages, error messages, dialogs, import summaries, tooltips, and accessibility labels.
4. Do not hard-code UI copy inside React components. Use stable translation keys.
5. Use English as a fallback if a locale or key is missing.
6. Provide an in-addon language selector unless a reliable host-app locale can be detected consistently. If relying on the host locale, document it and provide an override if practical.
7. Use locale-aware formatting for dates, numbers, and currencies, e.g. `Intl.DateTimeFormat` and `Intl.NumberFormat`. Keep internal values locale-neutral.
8. Do not parse source data using the current UI locale. Input parsing must follow the report format, not the language selected in the UI.
9. Make the layout resilient to longer translated strings; avoid fixed widths that cause clipping.
10. Add tests for locale loading, English fallback, and translation-key coverage.

## Translation key style

Use descriptive, stable names grouped by feature, for example:
- `app.title`
- `upload.selectFile`
- `source.select`
- `preview.title`
- `validation.error.invalidDate`
- `export.download`
- `import.confirmTitle`
- `settings.language`

Avoid using full English sentences as keys when practical. Do not use translation text as program logic.

## Adding a new language

To add a locale:
1. Create a locale file based on the English key set.
2. Translate all keys.
3. Run the locale coverage test.
4. Check layouts with long translated strings.
5. Update the language selector and documentation.

## Suggested initial UI language

If the host app provides a reliable locale, use it as the initial preference only if behavior is predictable. Otherwise default to English and provide a visible language selector. The selected language should be easy to change.
